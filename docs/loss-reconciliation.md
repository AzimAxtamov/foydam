# Балансовая реконсиляция потерь (отчёт «Сколько Uzum вам должен»)

> Заменяет прежний расчёт по `quantityMissing` из карточки SKU.
> **`quantityMissing` МЁРТВ:** поле deprecated в OpenAPI-спеке и всегда возвращает
> `0` — старый отчёт по потеряшкам был нерабочим (всегда ноль). Формула ниже
> валидирована на реальных данных бета-селлера (3 SKU, сверка с физическим
> подсчётом, 4 независимых источника сошлись).

## Формула (на 1 SKU)

```
lost = accepted − removed − sold − defected − stock
```

Если `lost < 0` — это **не потеря, а рассинхрон снапшота**: клампим в `0` и пишем
`warning` с `skuId` для разбора. Селлеру отрицательное НЕ показываем.

## Источники компонентов (не выдумывать поля — только эти)

| Компонент | Источник | Правило |
|-----------|----------|---------|
| `accepted` | `GET /v1/invoice` | Сумма `quantityAccepted` по `skuForInvoiceDtoList`, **только** записи где `invoiceStatus.value == "ACCEPTED"` (записи `CREATED` исключить). |
| `removed`  | `GET /v1/return`  | Физвывоз со склада. **Legacy-правило (обязательно):** если у родительского return-объекта `totalPackedAmount == 0` И `assembledDate == null` → берём `amount` строки; иначе `packedAmount`. |
| `sold`     | карточка SKU (`/v1/product/shop/{shopId}`) | `quantitySold` — это **уже НЕТТО** (после клиентских возвратов), дополнительно ничего не вычитать. |
| `defected` | карточка SKU | `quantityDefected`. |
| `stock`    | карточка SKU | `quantityActive` (текущий остаток). |

### Матч SKU между источниками — ТОЛЬКО по `skuTitle`

Поле `id` в накладных (`SkuForInvoiceDto.id`) и в возвратах (`SellerReturnItemDto.skuId`)
— это внутренние идентификаторы строк, **они НЕ равны** `skuId` карточки и не равны
между собой. Матчить исключительно по `skuTitle`.

## Пагинация `/v1/invoice` и `/v1/return`

- Обе ручки отдают **голый JSON-массив** (не envelope с `payload`/`totalElements`).
- `size=50` (максимум по спеке), `page` с `0`. Тянуть **все страницы до неполной**
  (у активных селлеров 70+ записей). У этих ручек `totalElements` нет — идём до
  страницы короче `size`.

## Типичные ошибки (не перепутать)

1. **`quantityReturned` в карточке = клиентские возвраты**, это НЕ вывоз со склада.
   В формуле НЕ использовать. Вывоз считается только из `/v1/return` по legacy-правилу.
2. **`quantitySold` ≠ брутто-заказы.** Не выводить `sold` из `finance/orders`
   вычитанием возвратов — брать готовое нетто-поле карточки.
3. **`quantityMissing` — deprecated, всегда 0.** Никогда не использовать в формуле.

## Денежная оценка потери

Две суммы (как раньше):

- `lost × sellPrice` (`price` карточки) — считаем всегда, показываем как «к взысканию».
- `lost × COGS` — **COGS = себестоимость, введённая селлером у нас**. В **Фазе 0
  ввода себестоимости нет** → всегда `0`, показываем «закуп не указан».
  ⚠️ `purchasePrice` из API **НЕ подставлять** — поле грязное (селлеры не заполняют
  или заполняют мусором). Ввод COGS появится в Фазе 1.

## Компенсации

Компенсаций за потерю в Seller API **нет вообще** (проверено на полном леджере
`expenses`). Отчёт показывает полный `lost × …` как «к взысканию» и добавляет строку:
**если по позиции уже была компенсация от Uzum — селлер вычитает вручную.**
Не пытаться находить/зачитывать выплаты.

## Грабли API (подтверждены живьём, для будущего финансового синка)

- **Даты в параметрах `finance/orders` и `finance/expenses` — epoch СЕКУНДЫ**, а даты
  в ответах — epoch МИЛЛИсекунды. Если прислать миллисекунды в параметрах — сервер
  молча вернёт пусто (`200`, ноль записей, без ошибки). Делить millis на 1000.
- **`finance/expenses`: `payload.totalElements` возвращает `0`** даже при непустых
  данных — пагинацию вести **до пустой страницы**, не по этому счётчику.
- **`skuId` присутствует только в `finance/orders?group=true`**; в построчном
  (`group=false`) его нет — join item↔SKU только по `(productId, skuTitle)`.
  SKU, которого нет в ответе `finance/orders` = ноль заказов, а не ошибка.

## HTTP-клиент Uzum

- **Параллелизм ≤ 3** одновременных запросов (`UzumApiOptions.MaxConcurrency`,
  общий гейт на процесс). При большем Uzum рвёт коннекты.
- **Ретраи срабатывают на разрыв соединения** (`HttpRequestException`: socket reset,
  край Uzum закрывает keep-alive), а не только на HTTP-статусы `429/5xx`.
